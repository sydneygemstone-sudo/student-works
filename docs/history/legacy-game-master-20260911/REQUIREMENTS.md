## 游戏定位

两位孩子在课堂中，各用一台 iPad，联网合作玩一个 3D 游戏。Leesha 操作海盗，Quinton 操作潜水员。海盗负责船上的食物准备和防守，潜水员负责水下探索和收集；两人的工作相互支持。

今天将西瓜、鱼、珊瑚和水下收集合并为同一游戏。Dean 指定从下节课起再让两人分别开发不同游戏；当前不创建两个独立作品。

孩子对 Minecraft 有兴趣，这是兴趣背景；本次明确玩法是岗位不同的合作游戏。画面要求为立体 3D，操作应适合尚不熟练使用 iPad 的孩子，少依赖文字说明，由课堂主持辅助引导。

## 已明确的角色分工

| 项目 | Leesha：海盗 | Quinton：潜水员 |
| --- | --- | --- |
| 活动位置 | 在船上，不下水 | 下海探索，并能回到船上交接和补给 |
| 主要工作 | 切西瓜、准备食物、给返回的潜水员补给 | 在有鱼和珊瑚的海里抓鱼、收集宝石和星星 |
| 合作交接 | 接收潜水员带回的星星，提供西瓜 | 把星星带回交给海盗，接受西瓜补给，再下水 |
| 危险 | 怪物会撞船，需要赶走 | 海里有鲨鱼，需要躲避 |
| 已提到的应对方式 | 用大炮赶走撞船的怪物 | 使用加速器加速，躲避鲨鱼 |

课堂还提出了**西瓜枪**。该想法保留，但谁使用、打什么、是否消耗食物西瓜尚未明确，不擅自归入某个角色。

## 食物、收集与整局胜利

- 西瓜是食物资源。两人饿了、缺少西瓜补给时，不能继续收集星星和宝石。
- 海盗切西瓜，潜水员回船后得到补给，形成可以反复进行的工作循环。
- Quinton 已提出星星在海底最下面，看到就可以拿；具体触屏操作尚未定。
- 两人合作收集齐 **5 个宝石和 2 个星星，赢得整局游戏**。这是 Dean 已确定的规则，不再询问是赢一轮还是赢整局。
- 宝石和星星当前是收集目标。老师提及代币/货币用于讲解，不意味着已经决定购买、兑换或商店机制。
- 潜水员回船交星星已明确。宝石是否也必须带回、胜利计数是在拾取时还是交船时结算，需要在设计中写清。

## 已形成的玩法循环

海盗准备西瓜并守船 → 潜水员下海抓鱼和寻找宝藏，躲避鲨鱼 → 潜水员回船交接星星、获得食物 → 继续出发 → 达到共同收集目标后赢得整局。

上述箭头说明资源交接。Dean 正在询问孩子选实时一起玩还是回合制，目前尚无答案，不能根据岗位分工直接确定游戏时序。

西瓜已成为继续探索所需的补给；水下探索提供胜利目标；船上防守与水下躲避提供挑战。抓鱼功能仍保留，鱼对食物、奖励或胜利的作用尚未确定。

## 尚需设计补齐的部分

以下尚无明确课堂决定，不能写成孩子已经要求的规则。

| 缺口 | 实施前需要明确的内容 |
| --- | --- |
| 西瓜来源与饥饿 | 西瓜从哪里来、是否补充；饥饿如何变化，吃多少能继续工作 |
| 抓鱼的意义 | 如何抓、抓到后有什么反馈，鱼能做什么；不能悄悄删掉原始抓鱼愿望 |
| 西瓜枪与装备 | 西瓜枪归属、用途、与食物的关系；大炮和加速器的简单使用规则 |
| 遇险与恢复 | 鲨鱼碰到潜水员、怪物撞船后会发生什么；能否救援或重新开始，怎样避免无事可做 |
| 收集交接与操作 | 宝藏在哪一刻计入共同目标；两台 iPad 各自的移动、交互、镜头和主要按钮 |

建议下一步由 AI 提供一份简短的第一版玩法方案填补这些缺口，并标清建议与已确定要求；不把所有细节重新变成孩子必须回答的问卷。具体供应商、模型、预算与时间随后随执行方案确定。

## 用于后续验收的检查点

以下是依据本次目标整理的验收提案，不是已完成测试。

1. 两台实际 iPad 能进入同一局，一台操作海盗，另一台操作潜水员；各自行为和共享结果能够同步。
2. 实际呈现并能操作 3D 船上与水下场景，保留西瓜、鱼、珊瑚和两位角色，孩子能理解主要动作。
3. 海盗切瓜、潜水员返船交接与补给、再次下水的循环确实可玩；补给会影响继续收集的能力。
4. 潜水员能抓鱼和取得宝藏；鲨鱼、撞船怪物、大炮、加速器按定稿规则产生真实交互。
5. 西瓜枪在定稿时明确用途；如需分阶段制作，应清楚列出并获得对应范围决定，不能在交付时无声遗漏。
6. 两人完成 5 个宝石和 2 个星星目标时，两台设备都显示同一整局胜利结果，交接或重复输入不重复计数。
7. 按定稿规则验证遇险恢复及再玩；做一次实际断线/重进检查，记录合作游戏是否能继续。
8. 两位孩子实际试玩，分别确认自己的岗位可操作、能看到对方工作的作用。主控测试通过不替代孩子试玩。
